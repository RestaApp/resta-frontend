## Kill-правила

Помогают не влюбляться в свои идеи. Применяются механически, без обсуждения «а вдруг ещё чуть-чуть»:

1. **Нет эффекта 2–3 недели** (или полный отведённый срок из таблицы) → закрываем, `Finished-Lost`, записываем вывод. Перезапуск — только с новыми данными.
2. **Ухудшает UX или доверие** (жалобы, отписки, раздражённые управляющие) → закрываем сразу, не дожидаясь конца срока.
3. **Требует постоянной ручной работы основателя** и не автоматизируется → не масштабируем: либо переводим на помощника/бота, либо `Archived`. Иначе получается «диспетчер в Польше» (анти-цель стратегии).

---

**Главная честность этого документа.** На объёмах 20 ресторанов / 150 работников классический A/B со статзначимостью возможен только там, где единица теста — **пост в канале** (30–60 постов в месяц) или, с месяца 4–5, **смена** (50–150 смен/мес). Всё остальное — последовательные тесты «до/после» (2 недели baseline → включили → 2 недели замер), quasi-сравнения когорт или качественный сигнал (5–10 разговоров). В таблицах тип указан явно: **A/B** · **до/после** · **quasi** · **кач.** · **набл.** (наблюдательное — не эксперимент, просто фиксируем). Если у эффекта меньше ~30 наблюдений на вариант — не считать p-value, смотреть на величину эффекта и здравый смысл.

Правила запуска:

- Не больше **2–3 экспериментов одновременно** на одну стадию воронки — иначе результаты перемешаются.
- Каждый эксперимент до запуска получает строку в журнале (обычная таблица в Notion/Sheets): гипотеза, дата, вариант, метрика, результат. Без строки — не эксперимент, а суета.
- Все метрики — из своих событий в БД + Metabase (стратегия, «Что доделать» п.4). Пока событий нет — можно запускать только то, что меряется руками (посты, разговоры).
- Стоп-правило по умолчанию: если за отведённый срок эффекта не видно — выключаем и записываем. Второй раз ту же гипотезу не тестируем без новых данных.
- Колонка **Status** в таблицах: `Not started` → `Running` → `Finished-Won` / `Finished-Lost` → `Archived` (потеряло смысл / вытеснено другим). Статусы обновляются вместе с дашбордом §0.

## Growth Loops — петли роста

Это не эксперименты, а схемы, ради которых эксперименты существуют. Если петля крутится — рост идёт без ежедневных усилий; работа growth-менеджера — находить, где петля рвётся, и чинить разрыв конкретным номером из §1–§3.

### Loop 1. Смена как контент (главная петля)

```
Ресторан публикует смену
        │
        ▼
Авто-пост в канал (F1) ──► работники видят пост ──► тап по кнопке (№13)
        ▲                                                │
        │                                                ▼
Ресторан доверяет,                гость открывает карточку (startapp=shift_<id>)
публикует больше смен                                    │
        ▲                                                ▼
        └── смена закрыта быстро ◄── отклик (№28–42) ◄───┘
```

Где рвётся → чем чиним:
- пост не даёт открытий → №13–19 (кнопка, ставка, фото, каунтдаун);
- карточка не конвертит в отклик → №28–42;
- работник не вышел — доверие ресторана сгорает → S5/№43–53, страховка первых смен №80;
- смена закрыта, но ресторан не вернулся → №82–84, F10, разбор неудач №89.

### Loop 2. Передача смены (виральная петля)

```
Работник не может выйти
        │
        ▼
Жмёт «Передать смену» (F2) ──► друг получает личную просьбу (№65)
        ▲                                │
        │                                ▼
сам когда-то пришёл          друг открывает deep link,
по такой же передаче         аккаунт создаётся по пути (№67)
        ▲                                │
        │                                ▼
        └── новый работник ◄── смена закрыта, рейтинг передавшего цел (№69)
```

Где рвётся → чем чиним:
- кнопку скрывают, боясь наказания за отмену → №69 (передача не штрафуется), №71 (рассказать о механике заранее);
- получатель отваливается между тапом и принятием → №67 (померить воронку пошагово), №20;
- переданные смены проваливаются чаще обычных → №70 (порог рейтинга), №68 (уведомить ресторан).

### Loop 3. Данные → контент (петля доверия рынка)

```
Закрытые смены ──► реальные ставки в БД (S4)
      ▲                     │
      │                     ▼
больше смен        зарплатная сводка (F8; до 30 смен — данные опроса G1)
      ▲                     │
      │                     ▼
новые работники ◄── репосты сводки админами и рестораторами (G2, №5)
и рестораны
```

Где рвётся → чем чиним:
- данных мало, сводка неубедительна → G1 (опрос) как донор данных, №9;
- сводку читают, но не пересылают → №5 (картинка vs текст), №7, G8 («цена невыхода»);
- репосты есть, приток не атрибуцируется → F3, №27 (дисциплина ссылок).

Две честные оговорки к ICE:

1. **ICE недооценивает «множители».** S1 (помощник) со Score 36 стоит в середине таблицы, но остаётся пунктом №1 топ-10: он не даёт смен сам, он умножает всё остальное. Score — сортировка очереди, не замена здравому смыслу.
2. **Низкий Score из-за Confidence = Low ≠ «не делать».** F2 «Передать смену» — образцовый пример: Impact 9, но Confidence Low, потому что эффект никем не проверен. Ответ на Low Confidence — самый дешёвый MVP и замер (№67), после которого Confidence пересматривается и строка пересортировывается.

## Чего НЕ делаем (до 50 ресторанов / 500 работников / 500 закрытых смен)

- ❌ **Геймификация** (очки, уровни, ачивки сверх простых статусов №62 и бейджей надёжности №52) — на 150 пользователях играть не с кем; репутация работает, игра — шум.
- ❌ **Реферальные бонусы деньгами** — бюджета нет, а платная мотивация ломает работающую социальную («выручи», «передай смену») и притягивает накрутку.
- ❌ **Поиск/каталог маркетплейса** (витрина работников, фильтры, подборки заведений) — каталог нужен ликвидности, которой ещё нет; на 20 ресторанах все друг друга видят и так.
- ❌ **Премиум-аккаунты и любые платные функции** — `VITE_MONETIZATION=false` до M7, закон стратегии: просить деньги на пустом рынке — убить доверие.

Каждый пункт пересматривается ровно один раз — при достижении порога, не раньше и не «ну почти достигли».
