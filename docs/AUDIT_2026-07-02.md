## P1 — исправить до запуска

### 1. Infinite scroll реализован как растущий `per_page` — O(n²) трафик + бесконечный цикл запросов после 100 элементов
**Confidence: high** · `src/features/feed/model/hooks/useVacanciesInfiniteList.ts:32,45,47`

`per_page: visibleCount` при `page: 1` — каждый `loadMore` перезапрашивает весь список с начала; каждый `visibleCount` — отдельный cache-ключ RTK Query (`keepUnusedDataFor: 300`, `shiftsApi.ts:43`). Бэкенд клампит `per_page` на 100 (`shiftsApi.types.ts:79`): при `total_count > 100` `hasMore` остаётся `true` навсегда → `InfiniteScrollTrigger` зацикливает `loadMore` — неограниченный цикл сетевых запросов по 100 записей. `visibleCount` также не сбрасывается при смене фильтров.

**Impact:** гарантированный продовый инцидент по мере роста данных.
**Fix:** аккумулирующая пагинация (`serializeQueryArgs` + `merge`), `hasMore` от `next_page`, сброс при смене фильтров.

### 2. Удаление аккаунта недостижимо (мёртвая проводка)
**Confidence: high** · `ProfileSettings.tsx:294,343-347` рендерит строку/дровер удаления только при переданном `onDeleteAccount`; `ProfilePage.tsx` его никогда не передаёт (проверено). `useProfilePageModel.ts:39` возвращает `handleDeleteAccount` — не потребляется нигде.

**Impact:** пользователь не может удалить аккаунт — блокер запуска (GDPR/152-ФЗ, политики сторов).
**Fix:** прокинуть `onDeleteAccount={handleDeleteAccount}`; предварительно исправить P2 №25 (raw `fetch`).

### 3. Архивация уведомления ломает многостраничный кэш
**Confidence: high** · `src/services/api/notificationsApi.ts:85-93,147`

`getNotifications` схлопывает страницы в один cache-ключ с `merge`-append для `page > 1`; `archiveNotification` использует `invalidatesTags: ['Notification']` → refetch идёт с аргументами *последней* страницы → данные страницы N дописываются к уже накопленному кэшу.

**Impact:** дубли элементов (дублирующиеся React key в `NotificationsDrawer.tsx:180`), устаревшие страницы, заархивированный элемент остаётся видимым.
**Fix:** оптимистичное удаление из draft (как `markNotificationRead` в `:112-137`), убрать tag-инвалидацию.

### 4. Focus-эффект Modal завязан на нестабильный `onClose` — фокус срывается во время набора текста
**Confidence: high** · `src/components/ui/modal.tsx:82-142`

Deps эффекта focus-trap включают сырой `onClose`; любой inline `onClose={() => ...}` перезапускает teardown (`prevActive?.focus()`) + рефокус первого focusable при каждом ре-рендере родителя. Паттерн `onCloseRef`/`stableClose` есть в `:69-73`, но здесь не используется; `alert-dialog.tsx:111` делает правильно (`[open]`).
**Fix:** ref в `onKeyDown`, deps `[isOpen, closeOnEsc, initialFocusSelector]`.

### 5. Drawer объявляет `aria-modal="true"`, но не имеет focus trap / initial focus / restore / accessible name
**Confidence: high** · `src/components/ui/drawer.tsx:269-271`

Клавиатура/скринридер уходят Tab'ом в визуально скрытый фон; дроверы несут ключевые флоу (фильтры, создание смены).
**Fix:** вынести trap из Modal в общий `useFocusTrap`, связать `DrawerTitle` id через a11y-контекст по образцу `ModalA11yContext`.

### 6. Черновик редактирования профиля не сбрасывается после успешного сохранения
**Confidence: high** · `EditProfileDrawer.tsx:78-86` — `resetForm()` вызывается только в `handleDrawerOpenChange`; успех закрывает дровер через родительский `setIsEditDrawerOpen(false)` (`ProfilePage.tsx:129-136`), минуя его. `draftFormData`/`hasAttemptedSave`/`fieldErrors` переживают сессию; устаревшие значения черновика повторно отправляются как diff.
**Fix:** `resetForm()` в success-ветке или по `open === false`.
