## FALSE POSITIVE / уже исправлено в текущем коде

- **A: «нужна dev-зависимость для компонентных тестов».** `@testing-library/react`, `@testing-library/dom`, `jest-dom` уже установлены; существующие и новые компонентные тесты исполняются. Дополнительная установка не нужна.
- **A: отклонённая заявка показывает «в обработке», теряется название, доступен повторный отклик.** На текущем фронте в браузере подтверждены «ОТКЛОНЕНА», сохранённое название и отсутствие кнопки повторной подачи. Есть тесты `applicationStatus`. Это не подтверждает корректность неизвестного старого деплоя. Рабочая backend-ветка отдельно меняет правило повторной подачи — см. ниже.
- **A: двойное подтверждение отклика (toast + экран).** В ленте `useShiftActions` уже вызывает `useShiftApplication({ showApplySuccessToast: false })`; отдельный overlay деталей показывает toast, но не второй success-экран. Тест режима без toast проходит. Реальную заявку ради проверки не отправляла.
- **A: рамка кнопки онбординга «всё ещё кривая».** Текущий `RoleTourOverlay` отслеживает `getBoundingClientRect()` во время spring-анимации навигации и ограничивает рамку viewport. В Chrome при ширине 390 рамка вокруг «Лента» корректна. На исходном Telegram iOS устройстве статус остаётся непроверенным.
- **A/B: уведомление не открывает смену с другого экрана.** В текущем коде drawer использует `openGlobalShiftDetail`, а `DetailOverlayRenderer` расположен глобально в Dashboard. Проверены код и тесты целей уведомлений. Полный прогон на трёх ролях с реальными уведомлениями не выполнялся; это не заявление о проверке каждого production-сценария.
- **A: бесконечная цепочка «вакансия → заведение → все вакансии».** В текущем `VenueListingsDrawer` выбор локальный; `origin="venue-listings"` запрещает повторный вход в профиль, есть регрессионный тест. Дедупликация глобального overlay также уже есть.
- **B: истёкшая смена переоткрывается при отказе принятому.** В текущем backend `ShiftApplication#reopen_shift!` при прошедшем `end_time` ставит `cancelled`, не `open`; отказ принятому на completed/cancelled уже блокируется. Новые frontend-ограничения закрывают недостающий UI-слой. Окончание по времени и серверный статус могут кратковременно различаться до фоновой обработки — это само по себе не доказывает переоткрытие.
